# HTTP 版本演进

> HTTP 各版本尽量保持方法、状态码和字段语义稳定，主要改进连接使用、消息分帧、压缩和丢包处理。

## 1. 总览

| 版本 | 典型传输 | 线路格式 | 并发方式 | 首部压缩 |
| --- | --- | --- | --- | --- |
| HTTP/1.0 | TCP | 文本 | 默认短连接 | 无 |
| HTTP/1.1 | TCP | 文本 | 持久连接，多连接并发 | 无 |
| HTTP/2 | TCP + TLS（浏览器常见） | 二进制帧 | 单连接多路复用 | HPACK |
| HTTP/3 | QUIC/UDP + TLS 1.3 | 二进制帧 | QUIC 独立流 | QPACK |

## 2. HTTP/1.0 与 HTTP/1.1

HTTP/1.1 默认使用持久连接，允许多个请求复用 TCP 连接，减少握手和慢启动成本。它还完善了 Host、缓存、范围请求、chunked transfer 等能力。

HTTP/1.1 pipelining 允许连续发送多个请求而不等待前一个响应，但响应必须按请求顺序返回。前面的响应慢会阻塞后面的响应，并且代理兼容、错误恢复复杂，所以浏览器没有广泛采用。

浏览器通常通过对同一 origin 建立多个 TCP 连接获得并发，这会增加握手、拥塞状态和服务器资源开销。

## 3. HTTP/2

HTTP/2 把一条连接中的数据拆成 frame：

- Stream：一条双向字节流，承载一次或多次相关消息。
- Message：请求或响应，由 HEADERS、DATA 等 frame 组成。
- Frame：线路上的最小协议单位，带 stream ID。

不同 stream 的 frame 可以交错发送，实现单连接多路复用。某个 HTTP 响应较慢不再要求应用层后续响应等待它完整结束。

### 主要能力

- 二进制分帧。
- 多路复用。
- HPACK 首部压缩。
- stream priority。
- server push。该能力在现代浏览器中缺少实际收益并已普遍停用，但仍可理解其协议设计。

HTTP/2 仍运行在单个 TCP 字节流上。TCP 丢失一个 segment 时，在缺失字节重传完成前，后续字节不能交给 HTTP/2，因此所有 stream 都可能被阻塞，这就是 TCP 层队头阻塞。

## 4. HTTP/3 与 QUIC

HTTP/3 把 HTTP 映射到 QUIC：

- QUIC 基于 UDP，在用户态实现可靠传输。
- 不同 QUIC stream 独立排序，一个 stream 丢包通常不会阻塞其他 stream 的交付。
- TLS 1.3 集成进 QUIC 握手。
- connection ID 让连接不完全绑定 IP 与端口，支持网络切换后的连接迁移。

HTTP/3 没有消除链路拥塞：不同 stream 仍共享连接级拥塞控制。它主要消除 TCP 字节流导致的跨 stream 交付阻塞。

## 5. HPACK 与 QPACK

HTTP 字段重复度高，首部压缩使用静态表、动态表和编码减少体积。

HPACK 依赖在有序 HTTP/2 连接上同步动态表。QUIC stream 相互独立，若直接复用该机制，引用尚未到达的动态表项会造成跨 stream 阻塞。QPACK 将编码器、解码器指令放在专用流，并限制可能阻塞的 stream 数量，以适配 QUIC。

## 6. 策略变化

- HTTP/1.1 中合并文件、雪碧图、域名分片用于减少请求或增加并发。
- HTTP/2/3 下过度合并会损害缓存粒度，域名分片会失去连接复用与压缩收益。
- 即使多路复用，资源优先级、JavaScript 执行成本和缓存策略仍然重要。

## Interview

### HTTP/2 是否彻底解决队头阻塞？

它解决了 HTTP/1.1 响应必须按序返回造成的应用层队头阻塞，但仍受 TCP 丢包引起的传输层队头阻塞影响。HTTP/3 通过 QUIC 独立流缓解后者。

### HTTP/3 为什么选择 UDP？

操作系统 TCP 难以快速演进。UDP 提供最小数据报能力，QUIC 可以在用户态实现可靠传输、拥塞控制、加密和多路复用，并更快迭代部署。
