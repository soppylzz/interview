# TCP 与 UDP

> TCP 提供可靠、有序的字节流；UDP 提供尽力而为、保留消息边界的数据报。二者不是“可靠与不可靠”这么简单，而是向应用提供不同抽象。

## 1. 对比

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 建立连接并维护状态 | 无连接 |
| 数据抽象 | 字节流 | 数据报，保留消息边界 |
| 可靠性 | 确认、重传、排序、去重 | 协议本身不保证 |
| 流量/拥塞控制 | 内置 | 应用自行决定 |
| 首次发送延迟 | 通常先握手 | 可直接发送数据报 |
| 广播/组播 | 不支持 | 可支持 |
| 典型场景 | HTTP/1.1、HTTP/2、数据库 | DNS、实时媒体、QUIC |

UDP 之上的应用仍可自行实现可靠性，例如 QUIC。TCP 之上的应用也仍需定义消息边界和业务级重试。

## 2. 三次握手

```text
Client                         Server
  | ----- SYN, seq=x --------> |
  | <--- SYN+ACK, seq=y, ack=x+1
  | ----- ACK, ack=y+1 ------> |
```

握手使双方确认彼此的收发能力，并同步初始序列号。两次握手不足以让服务端确认客户端能接收自己的响应，也更难避免旧 SYN 导致错误建立连接。三次已经可以完成双方信息确认，普通建立连接不需要四次。

## 3. 四次挥手

TCP 是全双工连接，两方向需要独立关闭：

```text
Active closer                  Passive closer
  | -------- FIN ------------> |
  | <------- ACK ------------- |
  | <------- FIN ------------- |
  | -------- ACK ------------> |
```

收到 FIN 只表示对方不再发送数据，本端可能仍有数据需要发送，因此 ACK 与本端 FIN 通常分开。若恰好可以立即关闭，ACK 和 FIN 可能合并。

## 4. TIME_WAIT

主动关闭方在发送最后 ACK 后通常进入 TIME_WAIT：

1. 若最后 ACK 丢失，被动关闭方会重传 FIN，主动关闭方仍能再次回复 ACK。
2. 等待网络中的旧报文消失，避免相同四元组的新连接误收旧数据。

大量短连接可能产生大量 TIME_WAIT，因此更合理的方向通常是复用连接、正确设置连接池，而不是简单取消协议保护。

## 5. TCP 如何保证可靠

- Sequence Number：标识字节位置，用于排序和去重。
- Acknowledgment：确认已收到的连续数据。
- Checksum：发现传输错误。
- Retransmission：超时或检测到丢包后重传。
- Sliding Window：允许多个未确认字节在网络中，提高吞吐。
- Flow Control：根据接收窗口避免压垮接收方。
- Congestion Control：根据网络状态调整发送速度。

流量控制保护接收方，拥塞控制保护网络路径。

## 6. TCP 粘包

TCP 只提供字节流，不保留应用写入的次数和边界。发送方两次 write，接收方可能一次 read，也可能多次 read。这不是 TCP 错误。

应用协议可使用以下方式划分消息：

- 固定长度。
- 分隔符。
- 长度前缀。
- 自描述格式。
- 连接关闭表示消息结束，但无法复用连接。

HTTP/1.1 使用 Content-Length、chunked encoding 或连接关闭确定内容边界；HTTP/2、HTTP/3 使用帧长度。

## 7. UDP 场景

UDP 适合应用更看重低延迟、允许丢失、需要自定义可靠性或使用组播的场景，例如实时音视频、DNS 和 QUIC。选择 UDP 不意味着完全忽略丢包、拥塞和安全，而是由上层协议处理。

## Interview

### TCP 为什么是字节流而不是消息协议？

TCP 负责可靠传送连续字节序列，并允许实现自由分段、合并和重传。应用消息语义属于更上层，因此必须自行定义边界。

### TCP keepalive 与 HTTP keep-alive 一样吗？

不一样。HTTP keep-alive 表示多个 HTTP 请求复用连接；TCP keepalive 是操作系统对长时间空闲连接发送探测包，用于判断对端是否仍可达。
