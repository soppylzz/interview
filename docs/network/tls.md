# HTTPS 与 TLS

> HTTPS 是通过 TLS 安全通道传输 HTTP。TLS 的目标是机密性、完整性和对通信身份的认证。

## 1. 密码学角色

| 机制 | 主要作用 |
| --- | --- |
| 对称加密 | 使用共享密钥高效加密大量数据 |
| 非对称密码 | 密钥交换、数字签名或身份认证 |
| Hash | 将任意输入映射为固定长度摘要 |
| MAC/AEAD | 检测消息是否被篡改并验证持有密钥 |
| 数字签名 | 私钥签名，公钥验证来源和完整性 |

TLS 并不是“用公钥加密所有 HTTP 数据”。握手阶段完成身份认证和密钥协商，应用数据主要使用高效的对称 AEAD 算法保护。

## 2. 证书与信任链

证书把域名、公钥、有效期、签发者等信息绑定在一起，并由 CA 签名。浏览器或操作系统预置信任根证书。

客户端验证服务端证书时至少关注：

- 当前时间是否在有效期内。
- 目标域名是否匹配 Subject Alternative Name。
- 证书签名能否沿中间 CA 链验证到受信任根。
- 证书用途和算法是否允许当前连接。
- 证书是否被撤销，具体检查受客户端策略影响。

根证书通常自签名，但被信任的原因是预装的信任锚，而不是“自签名本身可信”。

## 3. TLS 1.3 握手主线

```text
ClientHello
  - supported versions
  - cipher suites
  - key share
  - SNI / ALPN

ServerHello
  - selected version and cipher
  - server key share

EncryptedExtensions
Certificate
CertificateVerify
Finished

Client Finished
Application Data
```

双方用临时密钥交换结果派生会话密钥。服务端通过 CertificateVerify 证明持有证书对应私钥，Finished 验证握手记录未被篡改。

TLS 1.3 删除了许多旧算法与握手分支，完整握手通常比 TLS 1.2 少一个往返，并默认采用支持前向保密的密钥交换。

## 4. SNI 与 ALPN

- SNI：客户端在握手中说明希望访问的主机名，使同一 IP 上的服务端选择正确证书和站点。
- ALPN：双方协商 TLS 之上的应用协议，例如 `http/1.1` 或 `h2`。

ECH 可进一步保护 ClientHello 中的敏感信息，但部署与支持情况需要结合当前环境判断。

## 5. 会话恢复与 0-RTT

TLS 1.3 可通过 PSK/session ticket 恢复会话，减少完整握手成本。0-RTT 允许客户端在握手完成前发送早期数据，但早期数据可能被重放，因此只适合服务器明确允许、具有幂等或额外防重放保护的操作。

## 6. HTTPS 的边界

HTTPS 可以保护传输途中的内容并验证连接的服务端身份，但不能自动解决：

- 服务端自身被入侵。
- 应用中的 XSS、SQL injection、越权等漏洞。
- 用户设备上的恶意软件。
- 用户主动把凭据交给正确持证但恶意的网站。
- 流量大小、连接目标等全部元数据泄漏。

## Interview

### 为什么需要证书，只有公钥不行吗？

客户端需要知道拿到的公钥确实属于目标域名。证书和 CA 信任链为公钥与身份建立可验证绑定，否则攻击者可替换公钥并分别与双方通信。

### HTTPS 是否同时使用对称和非对称密码？

是。握手中的签名和密钥交换依赖非对称密码；协商出的会话密钥用于对称加密和完整性保护，以兼顾身份认证和传输效率。
