# 长连接与实时通信

> “实时”需要先明确通信方向、延迟、消息频率、浏览器兼容、代理环境和可靠性，再选择轮询、SSE 或 WebSocket。

## 1. 方案对比

| 方案 | 方向 | 连接方式 | 适用场景 |
| --- | --- | --- | --- |
| 短轮询 | 客户端主动查询 | 周期性 HTTP 请求 | 更新少、实现简单 |
| 长轮询 | 服务端延迟响应 | 每次响应后重新请求 | 兼容旧环境的通知 |
| SSE | 服务端到客户端 | 持久 HTTP 响应 | 通知、日志、文本事件流 |
| WebSocket | 全双工 | HTTP 握手后切换协议 | 聊天、协作、高频双向消息 |

## 2. Polling

短轮询固定间隔请求，无变化时也消耗请求和服务端资源；间隔越长，延迟越高。长轮询让服务器在有数据或超时后才响应，减少空响应，但仍需管理重连、挂起请求和代理超时。

轮询并非永远错误。低频状态、已有 HTTP 基础设施和对延迟不敏感的场景中，它最易观测和恢复。

## 3. SSE

SSE 使用 `text/event-stream` 返回 UTF-8 文本：

```text
event: message
id: 42
data: {"text":"hello"}

```

特点：

- 浏览器 EventSource 自动重连。
- `id` 可通过 Last-Event-ID 帮助断线续传。
- 单向传输，客户端仍用普通 HTTP 向服务端发送操作。
- 基于 HTTP，通常更容易穿过代理。
- 原生 EventSource 对自定义请求头等能力有限。

服务端和反向代理需关闭不合适的缓冲，并定期发送注释心跳，防止空闲连接被回收。

## 4. WebSocket

HTTP/1.1 中，客户端发送 Upgrade 握手；服务端返回 101 后，连接切换为 WebSocket 帧协议。HTTP/2、HTTP/3 环境可使用扩展 CONNECT，具体支持需看实现。

WebSocket 提供 message/frame 传输，但应用仍需设计：

- 用户认证与权限。
- 业务消息 ID、类型和版本。
- 心跳与失活检测。
- 断线重连、指数退避和抖动。
- 丢失消息补偿与重复消息去重。
- 消费速度和背压。

连接恢复后不是天然“无缝续传”。若业务不能丢消息，应记录序列号或游标，让客户端补拉缺失数据。

## 5. 三种 Keepalive

- HTTP keep-alive：复用传输连接承载多个 HTTP 请求。
- TCP keepalive：操作系统探测长时间空闲 TCP 连接是否仍存活。
- 应用层 heartbeat：双方按业务需要发送 ping/pong，确认应用仍可响应并维持中间设备映射。

三者目的和时间尺度不同，不能互相替代。

## 6. 选型

- 服务端通知、构建日志、AI 文本流：优先考虑 SSE 或普通 streaming fetch。
- 聊天、多人协作、游戏状态：考虑 WebSocket。
- 极低频状态检查：轮询可能更简单。
- 实时音视频：通常使用 WebRTC，而不是把媒体放进 WebSocket。

## Interview

### WebSocket 建立后还属于 HTTP 吗？

HTTP 用于协商和建立通道。成功升级后，连接传输 WebSocket frame，不再使用普通 HTTP request/response 消息语义。

### SSE 和 WebSocket 如何选择？

只需服务端推送文本事件时，SSE 自带重连并能复用 HTTP 基础设施；需要高频双向或二进制消息时，WebSocket 更合适。还需结合认证、代理、连接规模和恢复语义。
