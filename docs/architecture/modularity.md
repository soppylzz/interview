# 模块化与领域边界

按业务能力划分 feature module，每个模块公开小型入口，内部页面、状态和 API 不允许外部深层导入。Bounded context 的名称和模型可不同，通过明确 adapter 转换。

`shared` 只容纳真正跨领域且稳定的 primitive；业务 helper 放回所属模块，防止共享目录成为无主代码。

同步直接调用适合清晰依赖；事件降低发布者认知但隐藏控制流，需 schema、owner 和生命周期；command 表达明确意图。不要为“解耦”把所有调用改成全局总线。

先在单应用内模块化，只有独立团队、发布和运行隔离收益充分时再拆 npm 包、仓库或微前端。物理拆分不能修复逻辑边界混乱。
